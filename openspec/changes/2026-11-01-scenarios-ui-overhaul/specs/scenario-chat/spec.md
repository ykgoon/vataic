# Scenario Chat — Delta Spec

## ADDED Requirements

### Requirement: Scenario conversation
The web UI SHALL provide, on each scenario detail page, a conversation panel in which the user can ask questions about the stored scenario and its results. Each user message and each assistant reply SHALL be persisted per scenario with timestamps and re-rendered when the page loads. Sending a message and receiving a reply MUST NOT require a full page load (htmx swap).

#### Scenario: Ask about an outcome
- **WHEN** a user sends "Why is this outcome 18%?" in the panel of a completed scenario
- **THEN** the reply, grounded in the scenario's stored outcomes and factors, appears in the panel without a page reload and is persisted

#### Scenario: History survives reload
- **WHEN** the user reloads the scenario detail page after a conversation
- **THEN** the previous conversation is rendered from persisted storage

#### Scenario: Empty state
- **WHEN** a scenario has no conversation history
- **THEN** the panel renders with a prompt placeholder and no error

### Requirement: Conversation grounding
Each chat reply SHALL be generated by an LLM call whose context is composed from the scenario's stored data: premise card, selected factors with human names and current values, causal graph edges, outcomes with probabilities and summaries, and recent cycle summaries. The reply instruction MUST require grounding in stored data, plain language, and explicit acknowledgment when requested information is not recorded. Replies MUST NOT invent factors or outcomes that are not stored.

#### Scenario: Grounded answer cites stored data
- **WHEN** a user asks which factors drove the most probable outcome
- **THEN** the reply names factors from the scenario's stored factor set and outcome data

#### Scenario: Unknown information acknowledged
- **WHEN** the user asks about information that is not stored in the scenario
- **THEN** the reply states that the information is not recorded instead of inventing it

### Requirement: Conversation storage and lifecycle
The system SHALL store conversation messages per scenario (role, content, timestamps) and SHALL provide a control to clear the conversation. Clearing SHALL delete all stored messages for the scenario. Chat messages SHALL be removed together with the scenario when the scenario is deleted. If the LLM provider is unavailable, the panel SHALL show an error notice and MUST NOT persist the failed exchange.

#### Scenario: Clear deletes messages
- **WHEN** a user activates the clear control and confirms
- **THEN** all stored messages for the scenario are removed and the panel renders empty

#### Scenario: Provider failure shows error
- **WHEN** a user sends a message while the provider is unreachable
- **THEN** the panel shows an error notice, no assistant reply is added, and the failed exchange is not persisted
